Review of Sparkle Validator 1.2.0 against Sparkle 2.10.0, September 17, 2026.

The validator needs compatibility fixes and stronger regression coverage before claiming comprehensive Sparkle 2.10 support. The most urgent existing defects are shell injection in the GitHub Action and incomplete address filtering in the public fetch proxy. This review covers the core library, CLI, web source, Pages Function, schemas, tests, release automation, documentation, and bundled Homebrew formula. It does not verify the deployed website, published npm artifact, or separate Homebrew repository. Implementation files were not changed.

**What Sparkle 2.10.0 changes**

Sparkle 2.10.0 requires macOS 12.0. Its release announcement explicitly tells authors of manually maintained appcasts to add `sparkle:minimumSystemVersion` of at least `12.0` to affected items. It also fixes archive-length fallback when the server omits a content size and release-note length parsing for signed-feed diagnostics. These are reasons to exercise existing metadata carefully, rather than invent new XML fields. CocoaPods removal and the installer/delta implementation fixes do not themselves require new validator rules. See the [2.10.0 release announcement](https://github.com/sparkle-project/Sparkle/releases/tag/2.10.0) and [upgrade guide](https://sparkle-project.org/documentation/upgrading/).

Recommended compatibility work:

- Add explicit target metadata, such as a library option and CLI/web selection for the Sparkle version bundled in the update. For updates identified as using 2.10, diagnose a missing, empty, or below-12 minimum OS. `validate(xml)` currently has no such context. Do not reject all historical items below macOS 12: mixed feeds can legitimately retain older releases using older Sparkle versions.
- Add fixtures for a 2.10 release, a retained pre-12 release, missing and insufficient minimum OS, and signed external release notes. Distinguish the framework version bundled in an update from the version running in an existing client.
- Keep enclosure `length` unqualified and release-note `sparkle:length` qualified. Exercise missing HTTP Content-Length, matching and mismatched lengths, redirects, and timeouts with deterministic fetch mocks. The current remote extractor already reads qualified release-note length correctly.
- Describe the actual validation boundary: syntax, metadata, and optional HTTP checks are implemented; cryptographic verification of downloaded archives and signed feeds is not.

**Prioritized findings**

1. **P1 — GitHub Action inputs can execute shell code.** `action.yml:69`, `:74`, `:86`, and `:108` interpolate expressions directly into the Bash program. Double quotes do not prevent command substitution introduced during expression expansion. An input filename containing `$(printf ACTION_INPUT_EXECUTED >&2)` executed that harmless command in a local reproduction of the line, with the validator command replaced by `true`. This matters when a caller passes a filename or URL derived from untrusted workflow/event data. Bind inputs through environment variables, validate Boolean/timeout/format values, and build an argument array. Add an Action regression check for literal quotes, dollar signs, spaces, and command-substitution text. The Action also validates twice in text mode, potentially producing different network results and doing duplicate work; derive display and outputs from one invocation.

2. **P1 — Proxy address checks are bypassed by private IPv6 URLs and redirects.** `functions/api/fetch.ts:60` expects bare IPv6 text, but `:154` gets bracketed `URL.hostname` values and `:166` passes them through unchanged. Calling the actual transpiled handler with a mocked fetch allowed `http://[::1]/feed.xml`, `http://[fd00::1]/feed.xml`, and an IPv4-mapped loopback URL to reach the outbound fetch and return 200. Direct IPv4 loopback correctly returned 400. In addition, `:196` does not disable automatic redirects or check subsequent destinations. [Cloudflare documents that new requests follow redirects by default](https://developers.cloudflare.com/workers/runtime-apis/request/). Normalize and classify IPv6 properly, validate each redirect, and account for both A and AAAA records and the gap between DNS checking and fetching. These reproductions demonstrate application-filter bypass, not successful access to a private service through Cloudflare's deployed network.

3. **P2 — Proxy security tests do not test the proxy.** `test/api/fetch.test.ts:3` explicitly duplicates the helper instead of importing production code; consequently all 22 tests pass despite finding 2. Neither ESLint (`package.json:42`) nor TypeScript (`tsconfig.json:18`) includes `functions/`. Add runtime types and type/lint coverage for the Function, and test its exported handler with mocked DNS, redirects, chunked bodies, limits, and aborts. The CLI source fetch and proxy also lack explicit request/body deadlines (`src/cli/fetch.ts:5`, `functions/api/fetch.ts:84`, `:196`, `:259`).

4. **P2 — The XSD rejects correct Sparkle attributes.** `sparkle-appcast.xsd:131` and `:132` declare unqualified release-note `edSignature` and `length`; `:157` likewise declares unqualified critical-update `version`. Sparkle's published signed-note example uses `sparkle:edSignature` and `sparkle:length`, and this repository itself documents `sparkle:criticalUpdate sparkle:version="150"`. With the external XML namespace dependency replaced only in a temporary schema copy, xmllint rejected both signed-note attributes and the qualified critical version as “not allowed.” Use qualified attribute references and add fixtures for those exact documented forms. Apply the same correction to the public schema. See [Sparkle's publishing instructions](https://sparkle-project.org/documentation/publishing/).

5. **P2 — XSD validation is not self-contained, and negative tests conceal compilation failures.** `sparkle-appcast.xsd:27` fetches `http://www.w3.org/2001/xml.xsd`. In this environment the import failed, the schema did not compile, and 16 of 202 tests failed. The seven XSD rejection tests nevertheless passed because `test/xsd/schema.test.ts:18` treats any xmllint failure as an invalid document. Vendor the needed XML namespace schema, validate without network access, and distinguish schema/tool errors from document rejection. CI should explicitly install xmllint rather than silently skipping schema coverage when absent. With a local XML namespace declaration in an isolated temporary copy, all eight valid fixtures passed, confirming the immediate dependency failure.

6. **P2 — Rule-ID collisions hide unrelated diagnostics.** `src/core/rules/enclosure.ts:241`/`:254` and `system-requirements.ts:40`/`:56` both emit W011/W012. W042 is also shared by namespace variants (`structure.ts:71`) and enclosure-only versions (`version.ts:215`). `src/core/validator.ts:11` groups solely by ID and discards all but the first message, location, and fix. Reproduction with missing enclosure length/type and invalid minimum/maximum OS produced only enclosure warnings followed by “and 1 more similar issue”; the OS diagnostics disappeared. Give each rule a unique ID, retain individual occurrences in machine-readable results, and consolidate presentation separately. Update the README rule table and add a uniqueness/integration check.

7. **P2 — Effective version precedence disagrees with Sparkle.** `src/core/rules/version.ts:162` chooses the item element before the enclosure attribute. Sparkle chooses the enclosure attribute first. An item with element version 2 and enclosure version 1 followed by another version-1 item passed without duplicate or conflicting-version diagnostics. This also distorts ordering and date/version analysis. Use Sparkle's precedence and warn explicitly when the forms disagree. See the version-selection code in [SUAppcastItem.m at 2.10.0](https://github.com/sparkle-project/Sparkle/blob/2.10.0/Sparkle/SUAppcastItem.m).

8. **P2 — Valid namespace aliases are rejected.** `src/core/rules/structure.ts:52` requires the literal prefix `sparkle`, even though the parser and most helpers are namespace-aware. Replacing `xmlns:sparkle`/`sparkle:version` with `xmlns:s`/`s:version`, keeping the canonical URI, produced E004. Sparkle explicitly normalizes names by the canonical URI. Validate resolved namespaces rather than requiring a particular prefix; preserve actual namespace scope instead of relying on a document-wide prefix map. See [SUAppcast.m at 2.10.0](https://github.com/sparkle-project/Sparkle/blob/2.10.0/Sparkle/SUAppcast.m).

9. **P2 — Informational updates can pass with no usable destination.** `src/core/rules/enclosure.ts:126` exempts any item containing `informationalUpdate` from having either a link or enclosure. A versioned informational item containing neither returned `valid: true`; Sparkle rejects an item with neither an enclosure nor an information URL. An empty `<link/>` similarly counts as present locally. Require a usable destination. Review W017 too: its conditions inspect OS/upgrade elements outside `informationalUpdate` instead of that element's `version`/`belowVersion` children. See [Sparkle's item initialization](https://github.com/sparkle-project/Sparkle/blob/2.10.0/Sparkle/SUAppcastItem.m).

10. **P2 — Signed release-note metadata is unchecked by the core validator.** `src/core/rules/release-notes.ts:25` checks only whether notes exist. `sparkle:edSignature="not-base64!" sparkle:length="abc"` on a release-note link returned `valid: true` with no metadata diagnostic. Validate present signatures and lengths independently of whether signature-required mode is known. With an explicit signed-feed setting, also diagnose missing required metadata and make clear that format checking does not authenticate content. This is particularly relevant to the release-note length fix in 2.10.

11. **P2 — Signature-length arithmetic accepts malformed encodings.** `src/core/rules/enclosure.ts:35` permits arbitrarily many trailing `=` characters and `:48` infers decoded length from that padding count. A signature consisting of 87 `A` characters and five `=` characters passed E031 validation even though Node decoded it to 65 bytes. Strictly validate base64 grouping/padding and verify the decoded Ed25519 length. Test empty, excessive-padding, noncanonical, and wrong-length values. A mathematically inferred length is insufficient.

12. **P2 — URL validation is inconsistent with actual download/release-note behavior.** `src/core/rules/urls.ts:122` and `:138` inspect only the first localized note link. A valid English link followed by a German `javascript:bad` link returned `valid: true`. Iterate all localized links. `utils.ts:138` also defaults to allowing `feed:` for every context: an enclosure with `feed://example.com/app.zip` passed, although Sparkle's enclosure handling permits HTTP(S). Conversely, relative URLs are rejected even though Sparkle can resolve them against the appcast URL. Add feed/base-URL context and context-specific schemes. See [Sparkle's URL processing](https://github.com/sparkle-project/Sparkle/blob/2.10.0/Sparkle/SUAppcastItem.m).

13. **P2 — Declared Node support conflicts with dependencies and CI.** `package.json:56` promises Node >=18, while the installed Commander 14.0.2 requires >=20, Vitest 4.0.18 requires Node 20/22/24+, and Vite 7.3.1 requires 20.19+ or 22.12+. `.github/workflows/ci.yml:16` still includes Node 18 and explicitly runs tests there. Choose a supported runtime floor, align the engines/matrix/Action/release jobs, or pin compatible dependencies if Node 18 is an intentional requirement. The checks in this review ran on Node 22.23.2; Node 18 was not executed.

14. **P2 — The lockfile needs a security refresh.** The first successful `npm audit --json` returned 14 dependency findings: 3 moderate, 9 high, and 2 critical. The critical entries were Vitest and its dependent coverage package, not evidence of a production validator exploit. The [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp) applies to particular exposed UI/API or Windows UI/browser configurations. Refresh affected direct and transitive development dependencies, rerun the suite, and check the existing CI audit gate. Subsequent attempts, including `--omit=dev`, failed DNS resolution; this review does not claim a clean production-only audit.

**Completeness, documentation, and hygiene follow-ups**

- `src/core/rules/info.ts:12` treats `intel`, `universal`, and multiple architecture aliases as supported hardware requirements, with substring matching at `:138`. Sparkle's documentation describes the `arm64` constraint. Align accepted tokens with actual upstream behavior before presenting arbitrary values as enforced restrictions; `not-arm64` currently matches the known substring. Also validate empty/malformed `minimumUpdateVersion` rather than merely describing it in I007.
- `src/core/remote.ts:353` accepts zero/negative concurrency. With at least one URL, zero prevents the loop at `:361` from advancing. Require a positive integer. Move timeout cleanup into `finally` so failed fetches do not retain timers. Cover remote checks with controlled responses rather than predominantly skipped/live-network tests.
- `src/web/app.ts:185` renders clickable result-section headers as `<div>` elements with mouse listeners. Use keyboard-operable buttons with expansion state; add basic web smoke/accessibility coverage.
- `ROADMAP.md:3` still says 1.0.0, plans already-shipped URL checks, and reserves IDs already in use. Rewrite it around the actual 1.2.0 baseline and the proposed compatibility work.
- `RELEASING.md:16` runs `npm version patch`, which normally commits and creates the tag, then separately instructs creating the same tag. Use one consistent workflow, ensure Action/changelog changes enter the tagged commit, and build immediately before any manual publish. Its description of tag-triggered CI also differs from the workflows. Refresh the provenance fallback instructions and remove the curl-to-checksum pipeline that contradicts CLAUDE.md.
- `homebrew-tap/Formula/sparkle-validator.rb:4` still points at 1.0.0, has `PLACEHOLDER_SHA256`, and its test supplies an invalid one-character signature. Its README describes copying this template. Clearly mark/remove the obsolete template or update it; the separate live tap was not inspected.
- Generate public XSD copies from one source during the build. The root/public Sparkle schemas already differ in their version comment, and `tsup.config.ts` synchronizes only HTML/CSS.
- Update the appcast format guide with a 2.10 migration section and precise signature-validation scope. Make example fixtures executable checks so the qualified-attribute contradiction cannot recur. Separate placeholder signatures from examples advertised as directly valid.

**Verification and suggested order**

`npm run build`, `npm run lint`, and `npm run format:check` passed. `npm test` reported 186 passed and 16 failed, all failures in XSD compilation/validation because the external namespace schema was unavailable. `npm run test:xsd` reported 13 unexpected failures for the same dependency problem. Local reproductions used built library code, the actual transpiled proxy handler with mocked fetch, an isolated schema copy, and a harmless Bash input-expansion probe. No private-network probes, deployments, releases, or external messages were performed.

Address Action/proxy security first; restore deterministic schema and handler coverage; fix schema namespaces, rule IDs, version/namespace/destination handling; then add explicit 2.10 context, signed-note coverage, and documentation. Refresh the Node/toolchain baseline before the next release.
